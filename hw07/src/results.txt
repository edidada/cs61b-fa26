The linked-list map grows noticeably more expensive with N; each new key may
scan existing keys, giving quadratic total work. With well-spread hashes and
geometric resizing, MyHashMap has expected amortized constant insertion and
linear total insertion work. Ascending input damages an unbalanced BST but
does not inherently make hash buckets unbalanced. A hash map suits equality
lookup without ordered/range queries; a balanced tree offers sorted keys and
logarithmic operations even when hash distribution is poor.

All five bucket types complete successfully. These short single runs have
millisecond quantization, two-decimal output, JIT and ordering noise, plus
non-fixed random inputs. Zero means below displayed precision, not zero cost.
We cannot rank buckets reliably or claim a stable factor-of-ten ratio against
JDK HashMap from these rounded values. More controlled larger repeated paired
trials would be needed; these data do not prove asymptotic complexity.

Using HashSet as a bucket does not automatically speed up find: this map scans
Collection<Node> comparing node.key, and Node does not define key-based equality.
With bounded expected bucket length, replacing a scan by expected O(1) key-aware
lookup would change constants, not the already expected amortized O(1) map
bound. In adversarial long buckets an appropriate inner key index can reduce
search under its own hashing assumptions, but cannot promise worst-case O(1)
when all key hashes collide. Supporting that requires suitable key equality
and storage design, beyond simply swapping Collection implementations.
